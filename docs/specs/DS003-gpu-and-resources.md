# DS003 GPU and Resources

**Wording.** This text is carried from the local-llms specification at `34f8f498` with the hardware-limits content removed (local-llms keeps it, and the hooks that carry it into the engine are in DS007). "The agent" is the host program that embeds the engine; the `local-llm` agent of local-llms is the first such host. Paths such as `/data`, `/opt/runners` and `/shared/models` appear here as `dataDir`, `runRoot` and `sharedModelsRoot`, the `host` fields the agent fills with those values (DS007). Names such as `local_llm_run` are that agent's tool names for the controller operations of the same meaning (`run`, `status`, `overview`, `installRunner`, `addModel`, ...). The dashboard and the Settings page are the agent's plug-ins and are specified in local-llms.

## Introduction

This specification defines what the engine reads from the machine, how it decides whether a model fits before downloading anything, and how the runner processes are isolated. A host that limits CPU, memory or GPU shares binds the `limits` hooks (DS007); the engine itself applies no limit.

## Core Content

### GPU access

The engine reads the GPU the host gives it. `host.nvidiaSmi` is the path of `nvidia-smi` (null: no NVIDIA GPU is looked for), `host.nvidiaLibDir` the directory of the driver libraries (null: runners get no `LD_LIBRARY_PATH`), and `host.gpuAccess` explains why a device is missing: its `report(env)` answers `{ unavailable, reason }`, and the engine words it with the `gpuAccessReported` message (DS007). How a device reaches the process (a container runtime grant, a device node, a driver mount) is the host's business. When no usable GPU is found, the engine decides the `cpu` profile (DS005) and runs models on the CPU: it never fails to start, and never refuses to run only because no NVIDIA GPU is usable. If the GPU disappears while the engine runs under a GPU profile, the snapshot reports it unavailable and every Run is refused as `incompatible` until the engine restarts, which then decides the `cpu` profile.

### Hardware snapshot

A Vulkan GPU is considered only after NVIDIA is positively absent. The render node must be a character device under the platform's `devDriDir` (`/dev/dri` for `linuxPlatform()`). RADV uses an amdgpu render node on Linux. Venus uses the libkrun machine's virtio-gpu render node. `/dev/kfd` and display card nodes are not used.

The engine probes Vulkan only when `readGpu` returns `absent` and `/dev/dri` contains a character render node. A failed NVIDIA query never triggers a Vulkan fallback. A node with no valid Vulkan layout (`host.vulkan`, DS007) is `unusable`, and the reason is the `vulkanRuntimeMissing` message. `vulkaninfo --summary` must report exactly one accepted RADV or Venus device and no CPU or llvmpipe device. RADV is discrete unless the controller threads the exact `LOCAL_LLM_AMD_APU=experimental` switch through `readSnapshot` to permit integrated RADV. Without that switch, integrated RADV is refused before the runner device query. The Vulkan runner's device list must contain exactly `Vulkan0` with the same device name and safe memory figures. The snapshot adds `backend`, `driver`, `deviceType`, `vendorId` and `icdFile` only for Vulkan; it retains total, used and free bytes and an empty process list. An enabled APU reports `memoryModel: shared`, driver `radv`, and optional `deviceID`, `driverInfo` and `apiVersion` summary fields. Failed queries and malformed output remain unreadable and use the existing 60-second decision window.

APU admission counts device allocations once in shared physical RAM, plus the load staging copy and host runtime. Vulkan heap free bytes and the BIOS UMA carve-out never add physical headroom. The device figure is a separate mapping ceiling. Both driver and memory model must match the committed profile: `apu` requires shared RADV, while `vulkan` requires dedicated RADV. A mismatch refuses with restart guidance. APU allocation errors, guard stops or missing offload evidence never trigger an automatic CPU retry. DS005 defines the estimates and guard.

Vulkan probes run with a fresh environment containing only PATH, HOME, LANG, the explicit ICD files, disabled loader layers and disabled Mesa shader caching. Runner launches use one selected `VK_DRIVER_FILES`, `VK_LOADER_LAYERS_DISABLE=~all~`, and `MESA_SHADER_CACHE_DIR=<runRoot>/.mesa-cache`, alongside PATH, HOME, LANG and CUDA_CACHE_PATH. The Mesa cache stays outside `dataDir`. Vulkan launches receive no LD_LIBRARY_PATH, GGML_VK_VISIBLE_DEVICES or secrets. llama.cpp's Vulkan build uses loopback port 18086.

`lib/local-llm/controller/hardware.mjs` reads:

| Value | Source |
| --- | --- |
| GPU name, total, used and free memory, driver (and, when it cannot be used, its `state`: `absent`, `unusable` or `unreadable`; DS005) | `nvidia-smi --query-gpu` (the host's `nvidiaSmi`) |
| PCI device id, compute capability, addressing mode, utilization, power, temperature | a second, optional `nvidia-smi --query-gpu` (DS005) |
| Other GPU users | `nvidia-smi --query-compute-apps` |
| Total and available RAM | `/proc/meminfo` |
| Physical CPU cores | `physicalCoreCount()` (`cores`; DS005) |
| Free disk under `dataDir` | `statfs` |

Admission works on the physical figures of the snapshot. A host's limits can narrow them through the `capCores`, `decorateSnapshot`, `memoryPool`, `effective` and `admit` hooks, and can refuse a start (DS007); the hooks receive the physical figures. A GPU that gives no memory figures and is not known to share system memory is reported unusable with a reason that names the GPU and the values it gave, and models run on the CPU (DS005); when the device query fails, the GPU counts as unreadable instead. Without this rule every memory comparison was false and any model was admitted, whatever its size. A GPU that shares system memory (NVIDIA GB10 in DGX Spark) is detected as such and uses the unified profile (DS005); a GPU that reports numbers gives the same values as before.

### llama-server load mode

The llama-server adapters take `loadMode` (`auto`, `none`, `mmap`, `mlock`, `mmap+mlock`, `dio`), mapped one to one to llama.cpp's `--load-mode` (added in b10105; b10875 removed `--no-mmap`, `--mmap`, `--mlock` and `--direct-io`). `auto`, the dedicated default, passes no flag. ik_llama.cpp keeps its older flags and has no direct I/O: `none` is `--no-mmap`, `mlock` is `--mlock --no-mmap`, `mmap+mlock` is `--mlock`, and `dio` is refused. The former `noMmap` and `mlock` booleans are gone (LM Studio keeps its own `noMmap`, which its SDK takes as `tryMmap`). The model's training context caps `ctxSize` at `contextLength` per slot: a default above it (the schema's 16,384, or the catalog's recommendation) is lowered to it, and an explicit value above it is refused.

### Admission

`admit()` in `lib/local-llm/controller/admission.mjs` returns one of three answers, each with a reason and an estimate labelled `isEstimate: true`:

| Answer | Meaning | Example |
| --- | --- | --- |
| `ok` | The deployment fits now. A warning is attached when it needs more than half of the RAM available now. | gpt-oss-20b × llama.cpp at 16k context with 17 expert layers in RAM on a 6 GB GPU |
| `incompatible` | This machine can never run these parameters. The reason names the limit and the parameter to change. | 128k context with every expert on the GPU |
| `insufficient-now` | The hardware is enough, but memory or disk is held by something else at the moment. The reason names the other GPU users. | Ollama holding 4.5 GB of VRAM |

Estimates for llama.cpp come from the model's measured memory profile when the catalog has one (non-expert bytes, expert bytes per layer, KV bytes per token, fixed KV bytes), and from the file size otherwise. The gpt-oss-20b profile was measured on an RTX 3060 Laptop GPU (6 GB); for the default parameters the estimate is 4,851 MiB of GPU memory against 4,817 MiB measured. A 256 MiB GPU margin and a 1 GiB RAM margin are kept free. Admission runs when the overview is built, before a download starts, again after the controller's download, and last immediately before the runner starts: from a fresh snapshot, after the on-demand runner is prepared and the weights are checked for the last time (which can hash a large model for minutes), under the profile the Run was admitted with (DS005). GPU memory, RAM or disk that another process took meanwhile refuses the start (`insufficient-now`), the deployment ends in `error` with the reason, and no runner is started. For weights the runner fetches itself (Ollama) this last admission still counts the bytes left to fetch, and the adapter admits again once they are in, before it loads the model. The last admission is the one recorded on the deployment; vLLM takes its GPU share from it. A snapshot (up to three nvidia-smi queries in turn, each allowed 10 s, and a free-disk read) stops at once when its Run, pending or started, is stopped, cancelled or drained. The query in progress is killed, and the free-disk read, which cannot be cancelled, is not waited for. A stopped snapshot admits and launches nothing, and a Run stopped before its job started records nothing. A Stop or Cancel invalidates every Run submitted before it, including Runs still waiting in the command queue, so none of them is admitted, downloads or starts afterwards; a Run submitted after it is admitted as usual.

**The disk term** (C12, DS002). Every policy refuses `insufficient-now` when the bytes the weights still need, plus a 5 % reserve, exceed the free disk under `dataDir`. Those bytes come from the acquisition plan the weight store makes without hashing or copying anything: 0 for a file already verified in the store or adoptable in place at its canonical path; the full size for a private copy from `sharedModelsRoot` when there is no partial to resume (`copy`: a copy never links, so it always needs the space); the remaining bytes when a same-size `sharedModelsRoot` candidate sits beside a valid retained partial (`copy-or-resume`: a regular file whose identity record matches, holding at least one byte and no more than the pinned size), because the transfer makes the copy only when the whole copy and its reserve fit at that moment and otherwise leaves the candidate unread and resumes the partial (DS002), so a candidate, even a sparse one, never turns a resume that fits into a refusal; and the remaining bytes for a download or its resume. Run, its preview and the overview use the same plan, so they agree. The plan is only about disk: the memory and GPU checks come first and are the same whichever way the weights arrive, and nothing is hashed or copied before admission says `ok`. The copy and the download check the free space again before they write.

`admit()` makes the checks every runner shares (the runner is supported, the model has a source in the runner's format, a GPU is available unless the profile is `cpu`) and then calls the runner adapter's own policy: `admitLlamaServer` for llama.cpp and ik_llama.cpp (the same memory layout for the same GGUF file), `admitLmStudio` for LM Studio, `admitOllama` for Ollama, `admitVllm` for vLLM, and `admitTabbyApi` for TabbyAPI. A runner the release lists but cannot run is `incompatible` with the reason its adapter gives. A runner this deployment's operator left off (LM Studio without its switch) is `incompatible` with the switch's reason, before any estimate. In the `cpu` profile the runner's `admitCpu` decides instead (`admitCpuLlamaServer` for llama.cpp and its CPU build, `admitCpuOllama` for Ollama, DS005). A runner without one is `incompatible` because it needs an NVIDIA GPU.

`admitLmStudio` is the llama-server estimate plus 768 MiB of RAM for LM Studio's daemon and workers (about 0.6 GB measured at idle). It can reuse the llama-server model because LM Studio runs the same llama-server and the adapter sets every flag that affects memory. Through LM Studio's SDK it sets the context, parallel slots, unified KV, batch and micro-batch sizes, K and V cache types, flash attention on or off, mmap without mlock, and no context checkpoints. Through the SDK's argument override it sets the exact GPU layers, CPU MoE layers and threads. After each load the controller reads the engine's command line, and any flag that differs (the last value of a repeated flag counts), or an engine other than the pinned 2.41.0, fails the start with `runner_flags`. On the RTX 3060 Laptop, gpt-oss-20b at the llama.cpp runner's settings used 4,776 MiB of GPU memory on LM Studio, the same as on llama.cpp.

`admitVllm` keeps all weights on the GPU unless the admin sets `cpuOffloadGb`, which moves that many GiB of weights to system RAM with a warning that generation becomes much slower. It sizes the KV cache for `maxModelLen` from the model's `kvBytesPerToken` (halved for an fp8 KV cache) and adds 768 MiB for activations, the CUDA context and allocator slack, measured with Qwen3-4B-AWQ. CUDA reports about 94 % of nvidia-smi's total as usable. When weights, KV cache and overhead exceed 90 % of that, the model is `incompatible`; the reason names `maxModelLen`, a smaller model, or the least `cpuOffloadGb` that would fit. The GPU share vLLM gets (`--gpu-memory-utilization`) is the admin's value, or else what is free now less two margins, at most 0.9. If that share or the need exceeds what is free now, the answer is `insufficient-now`, naming the other GPU users. With `cpuOffloadGb` set, the system RAM estimate is (1.81 × the offload + 3.0 GiB) × 1.15. It comes from two runs of gpt-oss-20b with 10 GiB offloaded on the RTX 3060 machine (31 GiB of RAM, its 8 GiB swap already full). On 8080, available memory fell from 23.2 to 2.2 GiB, and `free` showed shared memory grow by about 18.1 GiB (1.81 × the offload: vLLM's pinned copies, more than any single process's RssShmem shows). The engine and API server held about 3.0 GiB more. In the fixture, available memory fell by at least 20.1 GiB before a guard stopped the run. An offload run must leave max(4 GiB, 10 % of RAM) available. When the estimate exceeds the available memory less that floor, the answer is `insufficient-now`; the reason names the estimate, what is available and the floor. When it exceeds total RAM less the floor, `incompatible`. The speed warning stays. On the 31 GiB machine, gpt-oss-20b (at least 9 GiB of offload on 6 GB) therefore needs 26.2 GiB available, so it is refused there in practice. The admission records the floor (`ramFloorBytes`), and the controller keeps a memory guard as the backstop. While such a runner loads, it samples MemAvailable every 2 s, and every 10 s once the runner is ready. If available memory falls below the floor, it stops the runner at once (SIGTERM, then SIGKILL within the drain's 3 s grace), and the deployment ends in `error` with "stopped: host memory below the floor (X GiB available, Y GiB required)". The first estimate (offload + 3 GiB, 13.0 GiB for 10 GiB) admitted a run that took the host down to about 2.2 GiB available with swap full. Without offload, the estimate stays 3 GiB with a 1 GiB margin, and there is no guard.

`admitTabbyApi` keeps all EXL3 weights on the GPU and sizes the KV cache for `cacheSize` tokens (the max sequence length unless set) at the `cacheMode` precision (Q8 a half, Q6 three eighths, Q4 a quarter of FP16), plus an estimated 640 MiB for the CUDA context and one prompt chunk's activations. ExLlamaV3 keeps the model's input embedding (`memory.embeddingBytes`) in system RAM, so that counts toward RAM, not the GPU. It is `incompatible` above the usable share of the GPU or the machine's RAM, and `insufficient-now` above what is free now.

### Runner isolation

| Rule | How |
| --- | --- |
| Loopback only | llama.cpp and ik_llama.cpp get `--host 127.0.0.1`; Ollama gets `OLLAMA_HOST=127.0.0.1:<port>` |
| Fixed ports | Each adapter declares its port; `defaultPorts()` refuses two runners on one port. llama.cpp 18080, ik_llama.cpp 18081, vLLM 18082, TabbyAPI 18083, LM Studio 18084 (its daemon also listens on 127.0.0.1:41343, and its engine on a random loopback port), Ollama 18434, llama.cpp's CPU build 18085 and its Vulkan build 18086, all on the loopback interface |
| Per-start credentials | llama.cpp and ik_llama.cpp get a fresh random `--api-key` on every start, and vLLM and TabbyAPI a key of their own; the chat responder reads it from the controller. LM Studio has none headless: its server relies on loopback and on the host keeping that interface private, and the controller keeps only its own model loaded |
| Minimal environment | Runners get `PATH`, `HOME=<dataDir>/home`, `LANG`, `CUDA_CACHE_PATH` and their own variables only; no secrets from the host's environment. `CUDA_CACHE_PATH` (`<runRoot>/.cuda-cache`) keeps the CUDA driver's JIT cache outside `dataDir`, which other processes may write (DS004). In the `cpu` profile a runner gets no `LD_LIBRARY_PATH` and an empty `CUDA_VISIBLE_DEVICES`, so the CUDA driver library is not loaded even where a GPU is attached but unusable. |
| OOM priority | Every runner's `oom_score_adj` is set to 1000 right after spawn, before it can load anything; its children inherit it. On a GPU that shares system memory, GPU allocations are invisible to RSS and the OOM score (DS005), so this is what makes an out-of-memory kill pick the runner. The mark is written through the platform's `setOomScoreAdj` (DS007). A runner that cannot be marked is killed; one that already exited is ignored. On the CPU the runner's memory is ordinary process memory; the mark still makes it the first victim, which matters on small hosts without swap (the Podman machine on a Mac has none). |
| Reaped on stop and drain | Each runner leads its own process group. Stop sends SIGTERM to the group, then SIGKILL after the grace period; when the runner exits, anything left in its group is killed, so helper processes a runner starts never outlive it |

### Rationale

#### Profile-based memory estimates

The GGUF header gives tensor sizes but not the CUDA compute buffers or the runtime's allocation behaviour, which differ by build and flash-attention mode. A profile measured on real hardware and stored with the catalog entry is accurate for the seed model; the file-size heuristic is the fallback for user models and is labelled as such.

The engine refuses before downloading when a model cannot fit, and keeps runners on loopback behind a per-start key.

### Diagnostic provenance

Unavailable GPU observations may include a diagnostic with code, backend, driver, source and a bounded message. Sources are `agent-query` (the engine's own query), `image-contract` (the host's declared runtime) and the `source` of `host.gpuAccess`. `gpu_access_unavailable` carries the host's sanitized text through the `gpuAccessReported` message; `gpu_unavailable` leaves the cause unknown and uses the `gpuAbsent` message. A render node with no valid declared runtime uses `vulkan_runtime_unavailable`, which says only that this host declares no supported runtime. Query failure uses `vulkan_query_unreadable`. Parser, topology, device-match and memory checks emit `vulkan_response_invalid`, `vulkan_device_unsupported`, `vulkan_device_mismatch` and `vulkan_memory_invalid` respectively. Driver identity is included only after an actual device observation.
