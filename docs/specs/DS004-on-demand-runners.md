# DS004 On-demand Runners

**Wording.** This text is carried from the local-llms specification at `34f8f498` with the hardware-limits content removed (local-llms keeps it, and the hooks that carry it into the engine are in DS007). "The agent" is the host program that embeds the engine; the `local-llm` agent of local-llms is the first such host. Paths such as `/data`, `/opt/runners` and `/shared/models` appear here as `dataDir`, `runRoot` and `sharedModelsRoot`, the `host` fields the agent fills with those values (DS007). Names such as `local_llm_run` are that agent's tool names for the controller operations of the same meaning (`run`, `status`, `overview`, `installRunner`, `addModel`, ...). The dashboard and the Settings page are the agent's plug-ins and are specified in local-llms.

## Introduction

A host's image can hold some runners (`host.executables`: llama.cpp, ik_llama.cpp, Ollama and the Vulkan build of llama.cpp). Heavier runners, the PyTorch-based vLLM and ExLlamaV3 + TabbyAPI, would add several gigabytes to every deployment, so an administrator installs them only where they are wanted. This specification defines what may be installed, where the files go, how they are checked, and when the runnable copy is rebuilt.

## Core Content

### What may be installed

The `vulkan`, `venus` and experimental `apu` profiles offer only the image-baked `llama.cpp-vulkan` build. It needs no Install step and has no lock entry. Every other runner is refused on those profiles before an install or model download. Vulkan availability requires the validated image contract and the image's executable, as described in DS005. The APU path uses the same Vulkan build; it adds no runner lock, download or dependency.

The host gives the image's lock as `imageRunnerLockFile` (schema `local-llm.runners-lock/v1`, `lib/local-llm/controller/runnerLock.mjs`; null: an empty lock), and may give one more lock per CPU architecture through `agentRunnerLockFile(arch)` (below). The engine has no default location for either: a missing file argument is refused with `missing_file`. For each installable runner a lock names the version, the kind (`python` or `archive`), the licence, every file with its URL, size and sha256, and the checks the CI install job runs. Administrators choose a runner id; they never supply a URL. The lock accepts only plain https URLs on `files.pythonhosted.org`, `github.com`, `codeload.github.com`, `download.pytorch.org`, `openaipublic.blob.core.windows.net` and `llmster.lmstudio.ai`, and each file is pinned by size and sha256 as well. A licence's `url` and `source` are plain https URLs: a UI shows them as links, so `javascript:` and `data:` never pass.

A licence may be marked `proprietary` (LM Studio): the software may not be redistributed, so it never ships in the image, and a proprietary entry must also require acceptance. The CI install check validates such an entry from the lock alone and never downloads it (below).

A `python` runner's files are wheels, source archives with `extract` (the directory they are unpacked into), and data files with `into` (the directory of the runnable copy they are copied into). A data file is something the runner would otherwise download when it runs. vLLM's `o200k_base.tiktoken`, the tokenizer vocabulary gpt-oss's chat format needs, is pinned this way into `tiktoken/`, and the vLLM adapter points `TIKTOKEN_ENCODINGS_BASE` there. openai_harmony then reads the file and checks its sha256 instead of fetching it from openaipublic (runners plan §6: nothing unpinned is downloaded at run time). vLLM loads harmony only on the first gpt-oss chat request, so a gpt-oss snapshot (`model_type` `gpt_oss`) is refused at start with `runner_incomplete` when the runnable copy lacks the file, for example an install from an older lock.

### Where the files go

| Part | Path | Lifetime |
| --- | --- | --- |
| Cache | `<dataDir>/runners/<id>/<version>/files/<name>`, and `installed.json`, the install record | Persists: the only part that survives a restart of the host's process environment |
| Runnable copy | `<runRoot>/<id>/<version>/`, on a filesystem the host does not share with other writers. The host creates `runRoot` and makes it writable by the engine's user. | The lifetime of that filesystem |

### Install

| Step | Rule |
| --- | --- |
| Start | `installRunner` with a runner id and `acceptLicence`. Who may call it is the host's business. Nothing installs automatically. One install runs at a time. |
| Operator switch | A runner whose adapter has one (LM Studio, `LOCAL_LLM_LMSTUDIO=internal-use`; vLLM on unified memory, `LOCAL_LLM_VLLM_UNIFIED=experimental`; DS005) is refused with `runner_disabled` while it is off, before anything downloads; the dashboard shows the reason and no Install. A switch may depend on the hardware profile. On an image that can run on unified memory, Install first tries to decide the profile from a snapshot, and an undecided profile keeps vLLM's switch closed. Only the amd64 image, recognised positively (a contract that does not say `architecture=arm64` and either names `ik_llama_cpp` or runs on an x64 CPU), never runs there, so while its GPU cannot be read vLLM stays enabled and installable (DS005). Uninstall still works, to free the disk. |
| Hardware profile | Install first decides the profile from a snapshot. In the `cpu` profile every runner without a CPU policy (DS005) is refused with `runner_unavailable` before anything downloads, and the dashboard shows why and no Install; the Runners tab's intro promises installs only while some runner can be installed under the profile. The dedicated and unified profiles add no such refusal: their runners are gated by their switches, as above. A runner that names the profiles it serves (llama.cpp's CPU build serves `cpu`) is refused the same way on any other profile, and is not listed there at all. An entry only the host's lock has is offered on the `cpu` profile alone (below). |
| Licence | A runner whose lock entry sets `requiresAcceptance` is refused with `licence_required` unless `acceptLicence` is true. The acceptance is recorded in the install state and in `installed.json`, with who accepted (the caller the host verified, never request input) and when. A UI shows the licence, its source link and the notice before the Install is sent. |
| Download | Each file goes through the downloader's resume, size and free-disk checks and is verified against its sha256 before it is used (`downloadFile`). The whole install first needs free space for the remaining bytes plus 5 %. A Stop, a drain or a network failure leaves the install `paused`; the next Install resumes the partial files. A server that answers a resumed request with 200 and only part of the file (LM Studio's download host does, with no `Content-Range`) makes the downloader discard the partial and start that file again from zero. |
| Record | `installed.json` is written only after every file verified. |
| Runnable copy | Built right after the download (below), so the install also measures the rebuild time. |
| Update | A new lock version is installed beside the old one. The old version's cache and copy are removed only after the new version is in place. |

### Runnable copy

Before the first launch in a container, and at the end of an install, `ensureRunnable` checks the copy's `.ready.json` marker. If the marker names this exact lock entry, the copy is reused, so a process restart in the same container does not rebuild. Otherwise:

1. every cached file is copied into container-local staging (`<runRoot>/.stage-<id>`) and hashed as it is copied; any difference from the lock blocks the rebuild with `cache_changed`. The steps below read only the staged copies, so a file replaced in `dataDir` after the check cannot reach the runnable copy;
2. the copy's directory is emptied;
3. a `python` runner gets a virtual environment from `host.python` (`uv venv`, with `host.uv`), and `uv pip install --offline --no-index --find-links <staging> --no-deps --require-hashes --no-cache` installs exactly the locked wheels; source archives are unpacked where the lock says, and data files are copied read-only (0444) into their `into` directory;
4. an `archive` runner's archives are unpacked, dropping one leading directory unless the file says `strip: 0` (LM Studio's llmster tarball has `llmster` and `.bundle/` at its root). File times are not restored (`tar --touch`, from `platform.tarFlags`, DS007): on the container's fuse-overlayfs, setting a directory's time fails with `EPERM`. A `.tar.zst` is first decompressed by Node's zlib (`createZstdDecompress`) into `<staging>/<name>.tar`, because the image has no zstd tool and the install steps give a process no stdin; tar then reads that file, and the staged `.zst` and the `.tar` are deleted as soon as each has been read. A stream that is not zstd ends the install with `install_failed` and no marker, and so does one that unpacks to more than 32 times its compressed size (and at least 1 MiB), which keeps a bad file from filling the container's disk. A stream that is cut short is reported by some Node versions and not by others: Node 24 fails with a zlib error (`Z_BUF_ERROR`, "unexpected end of file"), which is an `install_failed` like any other, and Node 25.8's decoder ends quietly with whatever it had decoded, down to an empty `.tar`. (Node 25.8 also decodes only the first frame of a stream of several, which looks the same.) So the decompressed `.tar` is checked on any Node by walking its headers from the start, and never reading a member's data (it seeks past it). Each header must be a ustar header: the `ustar` magic, and a checksum that adds up. Its member is skipped by the size field (octal, or GNU base 256), by the `size=` record of a pax extended header (`x` for the next member, `g` from there on), or, for a GNU long name or link header (`L`, `K`), by the header's own size; links, devices, directories and fifos carry no data, as GNU tar reads them. The tar is whole only when a block of zeros is found exactly where a header is due, followed by a second one, and the file does not end before that. Otherwise the install fails with `install_failed`. What a cut can leave (the end of the file where a header is due, a member or pax header that runs past the end, one block of zeros) is "decompressing … failed: it was cut short (…), or has more zstd frames than this Node decodes". What no cut of a whole tar can contain (a header without the magic or with a wrong checksum, a size that is not a number, a malformed pax record, a block of zeros followed by anything but a second one) is "decompressing … failed: it is not a ustar, pax or GNU tar this installer reads (…)". Either way the reason names what was found. Looking at the tail of the tar is no test: a member whose data ends in zeros, cut at its end, has zeros for its last blocks, and the archive would be marked ready without the members after it. The input is untrusted, so the walk is bounded: more than 1,000,000 headers (every header counts, so a writer that puts a pax header before each member reaches it at about 500,000 members), or a pax header over 1 MiB, is refused as such. An old V7 tar (no magic) is refused as a format the installer does not read. The sha256 pin covers the bytes on disk, and the launch-file check (next step) covers a wrong `strip`. Only the `.tar.zst` path needs this: gzip reports a cut stream itself;
5. the launch file is proven (below), the staging is removed and the marker is written last.

The launch file. A lock entry may name the file its adapter launches, `check.executable`: a plain relative path inside the runnable copy (`bin/ollama`, `llama-server`; no `..`, no absolute path). Before the marker is written the installer checks that it is there, that it resolves to a regular file inside the copy (a link that leads out of it is refused) and that it has an execute bit; otherwise the install fails with `install_failed` ("The unpacked … has no executable …"), the copy is removed and there is no marker, so the next Run tries again instead of launching nothing. A wrong `strip` or an archive that was cut short gives exactly such a copy, and neither zlib nor tar is sure to say so. The host's lock must name it for every archive entry; the image's lock may omit it (vLLM, TabbyAPI and LM Studio have no single binary that the check knows). A test holds each shipped entry's path equal to what its adapter's `buildLaunch` launches. "Executable" means the user that runs the engine can run it (`access(X_OK)`, not only a mode bit: mode 0645 has one and is no use to its owner). The launch file is part of the entry's digest when the entry names one, so a copy marked ready before the lock named it is built again and proven, and an entry that names none (every image-lock entry) keeps the digest it has always had, so nothing installed on a GPU host is rebuilt. Any failed build (the unpack, the size cap, a stop, a missing launch file) removes the partial runnable copy and the scratch directory `.tmp-<id>`, so the next attempt starts empty; both removals are tried, and one that fails is logged (`runner install: could not remove …`) and never replaces the error that led to it.

Only one build of a runner's copy runs at a time: a caller that arrives while it is being built (an Install finishing while a Run starts) shares that build. A Run on a runner whose install is in progress is refused with `busy`.

Every step runs in its own process group, so a Stop or a drain ends it. `uv` gets a minimal environment (`UV_OFFLINE`, `UV_PYTHON_DOWNLOADS=never`, no secrets). Code changed in the runnable copy lasts only as long as its filesystem, like code baked into the image; a new filesystem rebuilds the copy from the verified cache.

### LM Studio's runnable copy

The lock's `lmstudio` entry is llmster 0.0.25-1 with its bundled CUDA 12 engine, one tarball from `llmster.lmstudio.ai` (1,105,623,572 bytes, sha256 `46778639…`, `strip: 0`), under LM Studio's Terms, marked proprietary. The copy is the unpacked tarball, with no post-install step: llmster runs from it directly, without LM Studio's `install.sh` or `bootstrap`. Its home is `home/` inside the copy. On its first start in a container, llmster moves its engines out of the copy into that home, so the two share one lifetime: a rebuild or an uninstall removes both, and nothing of LM Studio's lives in `dataDir` except the verified tarball in the cache. The LM Studio SDK the adapter loads through is not part of the copy: it is the host's `lmStudioSdkDir`.

### Zstd archives

A `.tar.zst` is decompressed with Node's `zlib.createZstdDecompress`, which exists from Node 22.15 (the v22.15.0 documentation lists it as added there, and the v22.14.0 documentation has no zstd function). The package supports Node 22.13 and later, so the installer checks `typeof zlib.createZstdDecompress === 'function'` when it is used, not when it loads. Where the function is missing, an entry that lists a `.tar.zst` file is refused with the stable code `zstd_unsupported` and a message that names the runner, the file and the Node version; the refusal comes before anything is downloaded (`fetchAll`) and again before anything is unpacked (the runnable-copy build), so no partial copy, staging directory or marker is left. The controller asks the installer first (`assertSupported(entry)`): `installRunner` refuses before it writes any install state, and a Run on an installed runner whose copy has to be rebuilt refuses before it downloads weights, both with the same code. An install job records only the message of a failure, so the code could not reach the caller from the job. Runners whose archives are `.tar.gz` or wheels are not affected. A caller that passes its own `zstdDecoder` to `createRunnerInstaller` is used as given, and a test passes a `zlib` stand-in without the function to play an older Node.

### Uninstall

`uninstallRunner` with a runner id deletes the runner's cache and runnable copy, clears its install state and re-runs runner detection. It is refused while the runner runs a model, and it cancels an install in progress.

### The host's own runner lock

Besides the image's lock, the host may give one runner lock per CPU architecture: `host.agentRunnerLockFile(arch)` returns its file, or null for none. The controller asks for the architecture it runs on (`process.arch`) and reads the file as data, so nothing else in the code branches on the architecture. A runner can therefore become installable through an update of the host's own files instead of an image rebuild. How the host decides to trust an entry (a review, a CI gate) is its own process; the engine enforces only the rules below.

Entry rules are the same as the image lock: pinned by URL, size and sha256 on the allowed hosts; a licence and, where required, its acceptance; and an adapter in this release. Archives may be `.tar.gz` or `.tar.zst` (Ollama's releases); a `.tar.zst` is for archive runners only, never a python runner's source archive or data file. The host's lock must also name each archive entry's launch file, `check.executable` (above). Admins still choose a runner id, never a URL.

How the two locks meet:

- An id that is in both keeps the image's entry, and the controller logs the clash once at start. An entry only the host's lock has, for a runner whose executable the image already holds, is not offered either: the image's binary runs.
- A host lock that is a symbolic link is left out with a log line, like an invalid one: the lock must be a file of the repository revision, since a later change could point a link elsewhere without touching a path anyone reviews. (A directory above the lock may be a link.)
- A host lock that cannot be read or is not valid is left out with a log line, so a bad entry never stops the engine or takes the image's runners down with it. An invalid image lock still stops it, as before.
- An entry only the host's lock has is offered on the `cpu` profile alone, and only for a runner that has a CPU policy. The dedicated and unified profiles therefore show exactly the runners they showed before the host had a lock. Uninstall still works on any profile, to free the disk.

### Detection

A runner is installable when it is in a lock that applies (above) and this release has an adapter for it; a lock entry without an adapter (a runner a later release will run) is installed only by the CI install check. An installable runner is installed when its cache is complete and its record names the lock entry. Detection reads files only; it never imports Python packages. It runs again after every install and uninstall, so the overview follows without a restart. A Run on an installable runner that is not installed is refused with `runner_not_installed`.

### Install check

`pworker/local-llm/runner-install-check` exports `runInstallCheck(argv, { host })`. It resolves `{ report, code }` and never exits: the report is one JSON object, and `code` is 0 when every check passes and 1 otherwise. The same file runs as a script (`node lib/local-llm/tools/runnerInstallCheck.mjs <id> --lock FILE [--validate-only] [--require-executable] [--cache DIR] [--run-root DIR] [--uv FILE] [--python FILE] [--nvidia-lib-dir DIR]`), which prints the report and exits with `code`. The lock is `--lock`, or the host's `imageRunnerLockFile` when a host is given, and otherwise the check refuses with `missing_file`; the run root, the Python tools and the driver directory come from the host unless a flag names them. A CI job runs it for every entry of a lock inside the image that will run the engine, one entry at a time, on each architecture's own runner. Besides the libraries of the unpacked tree, it proves the launch file: `ldd` runs on it, and `--version` runs with the CPU environment (no driver library path, `CUDA_VISIBLE_DEVICES` empty) and must name the pinned version as a whole token (`0.34.40` and `0.34.4.1` do not name `0.34.4`); `--require-executable` makes an archive entry that names no launch file fail.

For a python entry it checks each pinned distribution's version and then every installed distribution against the lock's wheels: a distribution the lock does not name, one at another version, a locked wheel that is not installed, or one name installed more than once (a stale copy beside the locked one) fails the check (names compared as PEP 503 normalizes them; the listing keeps every installed copy). It imports the modules that load without a GPU, lists the ones that need the driver, and runs `ldd` on every shared object in the runnable copy. A library `ldd` cannot find passes only if the host's driver directory supplies it (`libcuda.so.1`), if another file in the same environment has that name (wheels load each other's libraries at run time, as torch loads its CUDA libraries), or if the lock entry lists it in `check.optionalLibraries` with the reason the runner never needs it (for example MPI and RDMA libraries for multi-node transports). Any other missing library fails the check, and the report lists all three groups. Every data file (`into`) must also be in the runnable copy with the lock's sha256.

A proprietary entry is never downloaded in CI, because downloading it would accept its terms on behalf of whoever runs CI. A CI job runs the check for it with no network and `--validate-only`, and the check itself also refuses to download any proprietary entry. It reports `downloaded: false` with what the lock pins: the files, their total size, their hosts and the licence fields. The install of such a runner is proven live, on a deployment whose admin accepted its terms.

### Rationale

#### Runnable copy isolation

`dataDir` survives restarts and, on a shared host, may be written by other processes. Rebuilding into the container's own filesystem from a cache that is re-verified against the image's lock means that code changed on disk never outlives the container, the same guarantee code baked into the image has. The check and the build use the same bytes: each file is hashed while it is copied into container-local staging, and the build reads only that copy, so a writer that swaps a cached file after the check gains nothing.

#### Pinned dependency closure

The lock already lists the resolved closure for this image's Python, so the install needs no resolver: every wheel is named with its hash, and nothing else can be installed.

#### CPU-only runner declarations

The two runners in the lock exist for the CPU: llama.cpp's CPU build has no GPU policy, and Ollama's arm64 build is the only way to run it on an image that lacks it. Offering them on the GPU profiles would add runners, Install buttons and table columns to hosts whose behavior this change keeps as it was, and a runner with no policy for the profile would refuse every Run. Keeping them on the `cpu` profile leaves the dedicated and unified overviews identical to what they were (a golden-file test in local-llms compares them with a file made before the lock existed, with both real locks loaded).

### Runner locks per platform (macOS)

A host on macOS gives the lock of its own CPU architecture as `imageRunnerLockFile`, not as the host's own lock: an entry only the host's own lock has is offered on the `cpu` profile alone (above), and the Metal build must be offered on the `metal` profile. The files are in `lib/local-llm-darwin/locks` (a host-side directory that moves with the host's other macOS files) and follow the Linux lock exactly: schema `local-llm.runners-lock/v1`, one archive entry, the launch file named in `check.executable`, and `strip` 1.

| Lock | Runner id | Release asset (llama.cpp b11295) | Size | sha256 |
| --- | --- | --- | --- | --- |
| `runners.lock.darwin-arm64.json` | `llama.cpp` (the Metal build) | `llama-b11295-bin-macos-arm64.tar.gz` | 11817829 | `1a0c5f60a3f2532a6d81c783bb18f11bac2925bc16dd605896b13fbabf4c7a56` |
| `runners.lock.darwin-amd64.json` | `llama.cpp-cpu` | `llama-b11295-bin-macos-x64.tar.gz` | 11372934 | `d14a2272a438aab97c0b184f4c371176ece01daf726a2589741d928f2fc0e456` |

Both were checked by downloading the asset, hashing it and reading the release's own listing. The macOS archives are `.tar.gz`, hold 18 relative library symbolic links, and the program finds its libraries through `@loader_path` and is ad-hoc signed; `tar` on macOS is bsdtar, which rejects `--touch`, so the platform passes `-m` (DS007). `test/local-llm-darwin/darwin-locks.test.mjs` loads both locks with the launch file required and pins every figure above. The arm64 lock was installed with the engine's own installer and `darwinPlatform()` on an Apple M1: the downloader verified size and sha256, `tar` unpacked with `-m`, and `llama-server --version` printed build 11295 and `--list-devices` an `MTL0` line. The Intel build was unpacked the same way and not run. The adapter of `llama.cpp` still carries the version `b11159`, which the runner summary shows beside the installed b11295: the engine compares an adapter's version with an installed one only for an executable the image holds (`probeVersion`), so nothing refuses, but the two differ on a Mac until the adapter's version follows the lock.
